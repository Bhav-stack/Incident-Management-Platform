
================ ingest load ladder ================
Each step: offered events/sec, how much of that stream the pipeline completed
while it was still being produced ('ordered_by_end_of_phase' - the sustained
rate it actually held), and the mean per-stage cost for the step. 'ordered'
means the event passed dedup, the out-of-order buffer and the rules.
'kept up' compares that against the events that were due by then: the offered
stream minus the 5s ordering window and the 1s flush tick,
which a pipeline that is keeping up still has in flight when the phase ends.

reading the numbers
  keep-up                : ordered_by_end_of_phase against the events due by the end
                           of the phase (offered minus window minus flush tick). Under
                           100% the pipeline is accumulating backlog, and past window +
                           grace that backlog is dropped, not delayed.
  drain_rate             : the backlog divided by the catch-up time, i.e. the
                           pipeline's own rate once the producer stopped competing
                           for the machine. Read it as the pipeline's capacity;
                           keep-up below it means the rig, not the pipeline, is the
                           limit for that step.
  dedup / buffer_offer   : paid once per received event, on the consumer thread
  rule                   : paid once per ordered sample, on the flush thread
  event_to_rule          : event time to rule evaluation. It includes the
                           deliberate 5s ordering window plus however long the
                           event waited to be produced and consumed, so it is a
                           staleness figure, not a processing cost.
  percentiles            : Micrometer publishes them over a rolling window, so
                           the table above describes the end of the run rather
                           than any single step; the per-step means are exact.
